# 底线清单（硬约束——禁止项铁律，全部为硬禁止，无豁免）

## 可执行性约束

所有条款必须可执行：明确动作、明确条件、明确结果。不可执行的条款视为无效。

## 一、语言铁律（硬禁止）

**全程简体中文**，专有名词/API/变量名/单位/期刊名可保留英文，其余一律中文。
**禁止全英文写作**：正文必须为简体中文，英文仅限专有名词。
违规 = 该条未落实。
bug 修复纪律：发现 bug 必须记录 bug 编号、根因分析和修复方案。

## 评估口径

合格基准：Sim/Umeyama 等基准测试必须明确评估口径，否则结果不可比较。

## 二、防 p-hacking（硬禁止）

- 禁止选有利指标、挑子集、调参优化报告指标
- 禁止基于初步结果调整假设后再声称是预设
- 禁止选择性报告：只报显著结果、隐瞒不显著结果
- **禁止p-hacking**：任何为显著性而调整的行为必须记入decision log
- 违反 = 该条标注 ❌ + 数据/结论作废

## 三、解冻纪律与数据纯净性（硬禁止）——归因先行

1. **code freeze 后改码必须解冻并记录**：freeze 状态下任何代码改动必须走解冻流程，写入 decision log
2. **改生成器 → 全量重生成 + 重训**：修改数据生成器代码后，所有数据集必须全量重生成，所有模型必须全量重训
3. **全量重测**：任何修改触发全量重生成、重训、重测
3. **禁掩盖**：禁止通过调整学习率、batch size、早停阈值等超参数反复试探来掩盖 bug
4. **留痕**：所有修复必须写 decision log + git commit + 报告"审查:"字段
5. **根因归因**：每次 bug 修复必须先定位根因再动手，先归因再修复
6. **范围限定**：bug 修复必须限定范围，禁止扩大修改面
7. **BUG-5 纪律**：同一 bug 重复出现 5 次以上必须升级处理，禁止反复热修，先归因再修复

## 四、落实证据必须引用文件:行号（硬要求）

证据字段必须引用 **真实存在、可验证的文件路径 + 行号/章节锚点**：
- 合格：`rules/判定铁律.md:29-35`、`.git/hooks/pre-commit:8-19`
- 不合格：只写文件名不写行号、行号与实际不符、路径不存在

## 五、档位约束（硬禁止）

档位使用必须符合 N0/N1/N2/N3 档位协议，禁止使用档位空间外的参数。

## 五、最小文件集等效执行

N0 档位为默认执行档位。zcode 等效平台缺省按「最小文件集」条款等效执行（无 skill/插件/MCP 也完整可跑），载体分散是推荐布局、不是运行前提。
